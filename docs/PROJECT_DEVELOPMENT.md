## 1. 产品目标、文档层级和完成规则

Atelier 是统一的 AI 创作 Web 应用：用户使用 Google 账号进入，围绕项目进行对话、文字构思、图片和视频生成、画布编排与素材管理；同一账户使用统一积分钱包；管理员在同一个前端管理用户、模型、供应商、定价、订单和系统设置。

本次用户明确要求：完整开发文档先落盘，然后逐步实现；每做完一步确认通过后，必须更新根目录 `nextStep.md`，便于跨会话、跨电脑继续。用户同时授权完成后初始化本项目并提交、推送至 `https://github.com/jasonlat-dot/atelier_canvas.git`。仍不打包，不发布生产服务。

### 1.1 状态含义

- **设计**：只有方案、接口草图或 UI 文案。
- **Mock**：演示流程，数据/模型/权限/收费为模拟。
- **内核通过**：纯逻辑有测试，不代表业务入口可用。
- **接线通过**：前后端契约与适配有验证，仍可能未连接数据库或真实上游。
- **联调通过**：开发环境真实数据库、认证、接口和页面跑通指定流程。
- **用户功能通过**：满足对应业务验收，错误恢复、权限、费用与持久化也通过。

下方任务的 `[x]` 仅表示任务所注明的范围完成；模块中的内核项不能使整个模块自动成为“用户功能通过”。每个阶段结束都记录：任务 ID、代码位置、命令、结果、未覆盖环境，以及下一步。

### 2.2 用户主流程

1. 用户在 Google 完成身份授权；Rust 验证后登录已有 Atelier 账户，或按注册策略新建 Atelier 账户。
2. 首次有效注册的奖励经服务端幂等入账；返回应用自己的会话与余额。
3. 用户新建项目，上传/选择素材，在画布编排或先与 Agent 讨论方案。
4. 服务端按模型能力验证参数与素材权限，返回带版本/有效期的报价。
5. 手动点击生成或批准 Agent 的准确工具请求后，服务端原子预占积分并创建幂等任务。
6. Worker 调度授权供应商，查询进度并将结果写入资产存储；完成结算或释放预占。
7. 用户在画布/素材库/用量页看到一致结果，刷新或换设备后能恢复。
8. 管理员在后台查到同一任务、路由、费用与审计；敏感变更有后端权限和审计。

Google 注册在本文指“使用 Google 身份创建 Atelier 用户”，不表示由 Atelier 代用户创建 Google 账号。

## 3. 技术架构与模块边界

| 层 | 技术与职责 |
|---|---|
| Web 界面 | React + TypeScript + React Flow；用户/管理员共用应用；交互状态与事件展示 |
| API 宿主 | Rust + Axum；认证、RBAC、租户隔离、应用服务与 HTTP/SSE |
| Agent 核心 | Rust 独立 crate，逐步复用 ShellPilot；模型协议、轮次、工具和上下文纯逻辑 |
| 数据与事务 | PostgreSQL + SQLx migrations；会话、项目、任务、账本、记忆、运营配置 |
| 任务 Worker | Rust；供应商调用、超时、恢复、幂等、产物保存，必要时独立进程 |
| 媒体处理 | 私有对象存储 + 后台缩略图/转码（FFmpeg 等实现后再验收） |
| 队列/通知 | 先确定可恢复任务/事件协议；数据库任务队列或独立队列方案按容量选型 |
| 支付 | Rust 服务端对接选定支付渠道，验签回调、订单与账本事务；具体渠道待定 |

新项目的业务后端和 Agent 就是 Rust。React 是浏览器界面层，与 ShellPilot 的 React 界面 + Rust 内核分工一致。Node/npm 当前用于前端开发工具，不是计划中的业务后端。

建议目录演进：`services/api/src/{auth,users,projects,canvas,chat,assets,generation,wallet,payments,subscriptions,catalog,providers,admin,audit}`；`crates/atelier-agent-core` 保持无数据库/SSH/HTTP 依赖；独立 Worker 达到需要时再拆。目录为规划，现有 handlers 大多仍在 `main.rs`。

### 4.2 Google 登录、注册与会话（AUTH）

- [ ] AUTH-01：配置 Google Web OAuth 客户端、同意屏幕、开发/正式回调 URL；ID 与 Secret 分环境管理。
- [ ] AUTH-02：Rust 实现授权发起、一次性 state/nonce、授权码交换与 ID Token 校验；使用成熟协议库；PKCE 按选定流程/库支持接入并测试。
- [ ] AUTH-03：以 Google `sub` 关联账户，校验签名、issuer、audience、expiry、nonce 及邮箱验证；邮箱变化不创建重复用户，不信任前端 email/role。
- [ ] AUTH-04：注册开关：关闭时禁止新账户，已有账户继续按状态登录；首次注册奖励只发一次，与注册事务或可靠事件关联。
- [ ] AUTH-05：邮箱范围策略可配置；旧说明提出仅 Gmail，是否包含 Workspace 见 DEC-01，不能把前端后缀判断当认证。
- [ ] AUTH-06：持久化应用 Session，限制有效期、轮换和撤销；退出、退出全部设备、禁用用户使会话失效。
- [ ] AUTH-07：登录/注册失败、拒绝授权、网络失败、重复回调、回跳地址和已禁用账户的页面状态。
- [ ] AUTH-08：生产移除 DEV_AUTH 路径与身份切换；写接口 CSRF/Origin 校验、限流，Cookie 使用 HttpOnly/Secure 并按 OAuth 回调实测 SameSite。

认证流程与 claim 校验以 [Google OpenID Connect 官方文档](https://developers.google.com/identity/openid-connect/openid-connect) 为技术依据。开发者需配置应用凭据与回调；应用 Session 由 Atelier 管理。Google API 的额外授权/离线访问不应因“登录”被默认扩大，参见 [Web Server OAuth 文档](https://developers.google.com/identity/protocols/oauth2/web-server)。

验收：假 Token、错误 audience、过期 Token、错误 state/nonce、回调重放均拒绝；同一 sub 并发注册只创建一人；封禁/退出后旧 Session 不可写；真实 Google 浏览器流程单独验收。

## 5. 数据设计与不变量

下表是目标领域模型。当前迁移仅包含 `users/projects/assets/generation_jobs/wallet_ledger` 基础字段；其余需新增迁移。已部署迁移不原地改写。

| 领域 | 目标表/实体与关键字段 | 必须保持的不变量 |
|---|---|---|
| 身份 | users、external_identities(provider, sub)、auth_sessions、oauth_attempts、roles/permissions | provider+sub 唯一；Session 可撤销；新建用户角色不可由客户端指定 |
| 项目 | projects(owner_id, revision, graph_schema_version)、canvas_snapshots | 更新需 owner+revision；项目删除不抹掉费用证据 |
| 会话 | chat_sessions、chat_turns(request_id, status)、chat_events(sequence, payload)、checkpoints | 用户+requestId 幂等；事件顺序单调、历史追加、检查点 CAS |
| 审批 | tool_calls、approvals(input_hash, quote_version, expiry)、dispatch_receipts | 准入绑定准确参数和当前权限；结果未知不自动复用授权 |
| 记忆 | memories(owner_id, scope, project_id, source, revision, enabled) | 用户确认、隔离、可编辑删除；摘要不能授权或直接写入 |
| 资产 | assets、upload_sessions、media_processing_jobs、asset_references | 私有归属；READY 前验证；临时 URL 不能作为永久对象 ID |
| 生成 | generation_jobs、job_attempts、provider_receipts、job_events | 每个业务任务幂等；租约防重复受理；终态与产物/资金一致 |
| 钱包 | wallets/projections、credit_reservations、ledger_transactions/entries、quotes | 整数金额；唯一业务键；不改历史；可用/预占/结算可对账 |
| 奖励 | reward_rules、reward_claims(user_id, kind, business_date) | 注册一次；签到用户/日期唯一 |
| 支付 | packages、orders、payment_attempts、payment_events、refunds | 渠道事件唯一；订单金额/币种快照；回调验签再处理 |
| 订阅 | plans、subscriptions、subscription_periods、entitlements | 周期唯一发放；权益与生效期一致；历史价目不可改 |
| 模型 | model_catalog、capability_versions、pricing_versions | 任务/报价绑定版本；停用不篡改旧任务 |
| 供应商 | providers、encrypted_credentials、routing_rules、health_events | 凭据不返回用户；路由受实时并发/配额约束 |
| 运营 | system_settings、audit_events、notifications、outbox_events | 修改有审计；业务事件可恢复投递、消费幂等 |

关联实体都需 owner/user 或受控平台权限；UUID 难猜不能代替权限。按 owner+time、session+sequence、状态+租约和业务幂等键建立索引/唯一约束；分页不能长期依赖无限列表。

### 5.1 钱包和任务的一致性

建议业务链：`报价 → 校验并预占 → 创建任务/可靠入队 → 供应商受理 → 产物保存 → 结算`；失败/取消按确认状态释放，未知状态进入核查。审批独立于扣费，不能仅批准就当作已消费。数据库与外部供应商之间不能假装存在跨系统原子事务，需要受理回执、outbox、幂等及补偿。

账本建议按不可变交易/分录记录积分从可用到预占、再到结算/释放的变化；余额是查询投影。具体实现与计价规则在 WALLET-01/02 固化，不沿用 Mock 的直接改余额作为正式钱包。

### 5.2 会话和任务事件

事件携带 `eventId/sequence/sessionId or jobId/requestId/type/timestamp`；游标恢复只返回当前用户授权范围。重复事件按 ID 幂等，缺口通过补拉历史恢复。停止生成、取消业务任务、拒绝审批为不同动作，界面与后端状态分别表达。

## 6. API 开发地图

统一前缀 `/api/v1`。现有接口仅指源码存在，不表示生产能力。所有资源身份由服务端 Session 取得；统一错误至少有 code/message/requestId，敏感细节不泄露。

| 分组 | 当前已有源码 | 目标新增/补齐（设计） |
|---|---|---|
| 健康/认证 | `GET /health`、`POST /dev/login`、`GET /me` | `GET /auth/google/start`、`GET /auth/google/callback`、`POST /auth/logout`、Session 列表/撤销 |
| 项目/图 | `GET/POST /projects`、`GET/PUT /projects/{id}/graph` | 项目详情/改名/归档/恢复、快照与导入校验 |
| Agent | `GET /agent/capabilities` | sessions/turns/history/events/cancel、approvals、context/compact、memories |
| 生成 | `POST /generation/quotes`、`GET/POST /generation/jobs`、`POST .../{id}/cancel` | 报价 ID/版本、任务详情/事件、受控重试、供应商回调 |
| 素材 | `GET /assets` | 上传申请/完成、详情/下载/删除、处理状态与分页 |
| 钱包 | `GET /wallet` | 预占/结算口径、流水分页、奖励状态/签到、quote 详情 |
| 目录 | `GET /model-catalog` | 真实能力/价格版本、用户可见过滤 |
| 支付 | 无 | 套餐、订单创建/查询、支付回调、退款申请与状态 |
| 订阅 | 无 | 计划、当前订阅、订购/变更/取消、周期权益 |
| 用量/通知 | 无独立真实接口 | 汇总/任务明细、通知/已读、授权搜索 |
| 后台 | 无正式管理 API | users/models/providers/pricing/settings/orders/subscriptions/audit 的受控接口 |

设计接口应在对应阶段形成请求/响应 DTO、权限、错误码、幂等键、分页、并发和事件契约。写接口返回是否真正提交成功，不能“先 Toast 成功再等后台”。财务/任务幂等键需绑定完整规范化请求，不能只比对 project/model/prompt。
